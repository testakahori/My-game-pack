## 自然湧きの修正

実サーバーで確認したところ、BridgeMODが毎tick自然湧きをオンに戻していた。UmetateMod 2.6.18では、研究室の識別ファイルを確認したワールドに限り、固定環境の処理後に自然湧きをオフにする。

Gitの旧コミットを `git archive` で取り出した別コピーでは、新しい実サーバー検証が自然湧きの項目で失敗した。修正版では、BridgeMODを含む実イベントバスを3回通してもオフを維持し、従来の復元・往復の検証もすべて通った。`npm run verify`（アプリ818件を含む）と4本のMOD契約テストも通過。

22:13に修正版を導入して通常のサーバーを再起動し、`gamerule doMobSpawning` が `false` と返ることを確認。導入したjarのSHA-256は `FC85A2ECBA86E0FFA378B763785BBD7AD766E2C3E00C3D40B257B3EE95F302A9`。

## リセット後のゲーム再開

2.6.18で、22:16:19にMinecraftのチャットから `/umetate reset` を実行し、22:16:23に完了表示を確認。接続を切らず、サーバーも再起動せず、22:16:40に `stackgame run nether_army 1` を実行して開始成功。状態は `active=nether_army`、`timedMobs=2`、BridgeAPIも登録済みのまま。

22:17:30にはイベントが実行中の状態で `umetate reset` を実行。22:17:35に復元が完了し、22:17:56には次の `nether_army` を開始できた。復元後も自然湧きはオフ。確認用のイベントをキャンセルして保存し、サーバーとMinecraftは利用できる状態で残した。

この確認でリセット後の追加再起動は不要と分かったため、復元処理は変更していない。利用手順に、完了メッセージの後はそのまま再開できることを明記した。

## 確認の範囲

今回の実画面確認は1人のクライアント、通常のForge描画で行った。マルチプレイヤー、再参加・再起動、床に穴がある場合の岩盤への着地、177450ブロックとブロックエンティティの復元は、先に実サーバーでの自動検証を通している。大量のゾンビや隕石を同時に発生させる負荷試験は今回の確認には含めない。

地獄滞在中・帰還時に3階を復元する処理は加えていない。復元は利用者が `umetate reset` を入力したときだけ行う。
