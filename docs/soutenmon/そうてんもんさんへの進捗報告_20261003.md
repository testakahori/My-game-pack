## 3. 要求の番号・個数・送信者名の扱い

### 同じイベントでも、別要求ならそれぞれ渡します

同じAさんから届いた要求でも、番号が違えば別の1件です。

| requestId | イベント | 送信者 | 扱い |
|---|---|---|---|
| 1001 | AquaTower | Aさん | 1件目 |
| 1002 | AquaTower | Aさん | 別の1件 |
| 1001の再送 | AquaTower | Aさん | ゲーム側で同じ1件と判定 |

BridgeMODは、eventKeyが同じという理由でゲーム要求を削除・統合しません。同じrequestIdの二重登録は、ゲーム側が自分の待ち列へ入れる時に防ぎます。そのための補助クラスとしてRequestLedgerを利用できます。

共通の即時イベントにも、eventKeyを理由にした削除は行いません。正常に届いたゾンビ召喚3件は、3件分を処理します。共通イベントにはrequestIdによる再送除外も設けていません。

### 大きなcountも、ゲームAPIでは1要求です

以前はcount=150を100と50に分けて送っていました。現在はゲームAPI経路であれば、count=150を1件のまま渡します。150回実行するか、1回の効果を強くするかはゲームMOD側で決めてください。範囲外の数値はエラーにし、黙って丸める処理は外しました。

ゲーム固有イベントのいいねも、条件達成ごとに別要求になります。例えば「100いいねでcount=2」なら、300いいね分はcount=2の3要求です。内部で待機情報をまとめて保持しても、ゲームへ渡す際は別々のrequestIdを付けます。

共通Mob召喚の負荷制御は残しています。gift・like・otherの3種類のキューと、tickごとの処理上限も維持しました。種類ごとの受付順を守り、種類をまたぐ処理には優先度があります。ゲームに渡した後の待機順と開始順は、ゲームMOD側で管理してください。

### ゲームMODへ渡す主な項目

| キー | 内容 |
|---|---|
| requestId | 要求の識別番号。文字列。再送中も同じ値 |
| key | ゲーム側のイベント名。ご提案のeventKeyに相当 |
| count | 整数1〜100,000 |
| listenerName | 送信者名。ご提案のsenderNameに相当 |
| type | gift・like・other |
| args | ゲーム用の追加引数。省略時は空のMap |
| gameSessionId | 要求を作った時点でアプリが把握していたゲーム開始番号 |
| announce | 表示を希望するかどうか。実際に表示する時点はゲーム側で決定 |
| server | サーバー内で渡すMinecraftServer |

HTTP受付ではsenderNameも使えますが、ゲームへの転送キーはlistenerNameです。互換用のeventIdにもrequestIdと同じ値が入ります。

argsは文字列・有限の数値・真偽値を最大32項目まで渡せます。入れ子や配列には対応していません。Bridge側では値の形式と上限を検証し、ゲーム上の意味は解釈しません。例えば強度を表すlevelが必要なら、argsの項目としてゲーム側で扱えます。

これらの仕様は、game.jsonのbridgeEventApiを1にしたゲームAPI経路が対象です。ゲーム側ではGameEvents.registerで受け口を登録します。旧方式のコマンド文字列を呼ぶ経路には、今回の無分割転送などの保証は適用されません。

## 4. リセット前の要求を次のゲームへ持ち込まないための変更

ゲーム内の待ち列だけを空にしても、Bridgeやアプリの待ち列は残ります。そのため、リセット前の要求が後からゲームMODへ届く可能性がありました。

この対策として、ゲーム開始ごとの番号を扱うAPIを追加しました。利用するゲームMODが、開始・終了・受付の各処理から明示的に呼ぶ方式です。

| ゲーム側の場面 | ゲームMOD側で行う処理 |
|---|---|
| 新しいゲームを開始 | GameEvents.beginSession(modId)で新しい番号を発行 |
| 終了・リセットして待機へ戻る | GameEvents.endSession(modId)で旧番号を無効化し、自分の待ち列を削除 |
| リセット後すぐ次のゲームを開始 | 自分の待ち列を削除し、beginSessionで新しい番号へ切替 |
| 要求を受け取る | 待ち列へ入れる前にisCurrentSessionで番号を照合 |
| 古い番号・欠けた番号を受け取る | DISCARDEDを返し、再送させずに破棄 |
| 一時停止 | 番号と待ち列を保持 |
| ゲーム継続中のプレイヤー死亡 | 番号と待ち列を保持 |

アプリは新規要求を作る際に番号を付けます。送信待ちやHTTP再送中も、その番号を書き換えません。古い要求を最新の番号へ付け直す処理も行いません。

ゲーム側の応答は、次の3種類です。

| 戻り値 | 意味 |
|---|---|
| WAIT = 0 | まだ引き受けていない。Bridgeに同じ要求を保持させる |
| ACCEPTED = 1 | 待ち列への登録済み。同じrequestIdを既に受け付けた場合もこれを返す |
| DISCARDED = 2 | 古いゲーム番号などで無効。再送不要 |

WAITを返す時点では、要求番号を登録済みにしないでください。登録前に番号だけ記録すると、後の再試行を重複として扱ってしまいます。

番号の状態通知は即時ではありません。新しい番号がアプリへ届く前の要求は、番号が空か古いため、ゲーム側で拒否される場合があります。開始時には新しい番号を発行し、アプリへ反映された後にイベントを受け付ける流れが必要です。

番号と要求履歴はメモリ内で扱います。サーバー再起動をまたぐ永続保存は未対応です。また、RequestLedgerの完了済み履歴には上限があります。無期限・無制限の再送除外を保証する仕組みにはしていません。

## 5. DisplayMODの呼び方と表示時間

ゲーム固有イベントのAPI転送時には、BridgeMODから先に表示しません。ゲームMODで順番が来た時に、DisplayMODとOBSMODをそれぞれ呼ぶ構成です。

```text
BridgeMODで受け付け
    ↓ 要求番号・個数・送信者名・引数を転送
ゲームMODの待ち列へ登録
    ↓ ゲーム側で開始可能と判断
ゲームMODの実開始処理
    ├─ DisplayMODを呼ぶ
    ├─ OBSMODを別に呼ぶ
    └─ ゲームイベントを開始
```

DisplayMODの公開APIは、`DisplayApi.show(Object server, Map<String, ?> payload)`です。BridgeMOD専用ではないため、ゲームMODから直接利用できます。任意導入にする場合は、同梱のOptionalDisplayヘルパーを使ってください。

例えば、実開始時に次のように呼び出せます。

```java
OptionalDisplay.show(server, Map.of(
    "title", "AquaTower 開始",
    "subtitle", "{ListenerName} さん ×{Count}",
    "listenerName", senderName,
    "count", count,
    "fadeInTicks", 0,
    "stayTicks", 120,
    "fadeOutTicks", 20,
    "sound", "minecraft:entity.experience_orb.pickup",
    "particle", "minecraft:happy_villager"
));
```

この例では、本表示120tickとフェードアウト20tickを指定しています。通常の20tick毎秒なら、本表示は約6秒です。省略時は、フェードイン／本表示／フェードアウトの順に10／70／10tickです。3項目の合計は1,200tick以下で指定してください。

表示時間を指定しても、途中で別のタイトルが来れば上書きされます。AquaTower表示の0.5秒後にゾンビ襲来が来た場合も、ゾンビ襲来へ切り替わります。最低表示時間の保護や優先度は、必要性を確認してからの追加対応です。

現在のタイトルは、接続中の全プレイヤーへ送ります。特定プレイヤーだけに出す指定は、今回のAPIにはありません。levelの専用表示項目もないため、必要ならゲーム側でタイトルやサブタイトルへ組み込んでください。

OptionalDisplayは未導入や呼び出し失敗時にfalseを返します。ゲーム側は表示の成否にかかわらず、イベントを続けてください。DisplayMODをmods.tomlで必須依存にすると未導入時にゲームを起動できないため、任意依存の構成にする必要があります。

DisplayMODはゲームの進行や待ち列を管理しません。OBSMODの存在も前提にしておらず、今回その内部実装は確認・変更していません。

## 6. アプリ側もゲームごとの設定に整理しました

アプリのTOPで「サバイバル・埋め立て・RUN・採掘」を選び、保存する流れにしました。ゲームを選ぶ欄はTOPだけに置いています。

保存後は、共通コマンドと選択ゲームで使えるコマンドを設定できます。対象はギフト、いいね、フォロー、シェア、訪問、未設定ギフト、通常ルーレット、デスルーレット、コメントです。例えば、サバイバルを選んでいる時に採掘専用のエンダーパールをルーレットへ登録する、といった取り違えを防ぎます。

割り当てはゲームごとに保存する方式です。ゲームを戻すと以前の設定を読み込みます。MODの切替はサーバーとMinecraftの両方へ適用します。サバイバルはBridgeMODとDisplayMOD、採掘はその2本にsaikutuMODを加えた構成です。

BridgeMODとDisplayMODはアプリの標準装備にしています。ゲームMODからDisplayMODを任意で呼べる仕様は、この配布方針とは別に維持しています。埋め立て・RUNの実際のゲームMODは未入手のため、その本体を使った切替・動作確認はまだです。

Minecraftの保存先は、標準の.minecraftと公式ランチャーの起動構成から候補を表示します。AIやドライブ全体の検索は使わず、手動でフォルダーを指定する方法も残しました。

共通の環境設定はBridgeMOD側で維持します。暗視、アイテムロストなし、昼・晴れ固定に加え、sendCommandFeedbackとcommandBlockOutputをfalseにしました。敵モブの自然発生を止めつつ、動物・魚の自然発生とギフト・コマンドによる召喚は残しています。既存のイベントによる一時的な時間・天候変更も維持しています。

## 8. そうてんもんさん側でお願いしたい接続作業

BridgeMODとDisplayMOD側の今回の改修は完了しています。ゲームMOD側では、次の接続をお願いします。

1. GameEvents.registerで受け口を登録し、要求をゲーム自身の待ち列へ入れる際にrequestIdを確認する。
2. ゲーム内リセットを扱う場合は、beginSession・endSession・isCurrentSessionを接続する。終了・リセットでは待ち列を消し、一時停止とゲーム継続中の死亡では保持する。
3. 各イベントが実際に始まる時にOptionalDisplayを呼ぶ。同じ場所からOBSMODも別に呼び、countの意味と開始順はゲーム側で決める。
4. 実際のMOD ID、イベントキー、追加引数、game.jsonの内容を合わせる。そのうえでStackingGame-Events本体との接続テストを行う。

こちらからは、受け渡し仕様とJavaの実装例を用意しました。OBSMODのSTART／END／CANCEL／RESETなどは、引き続きそうてんもんさん側での対応をお願いします。
