## 現在のコードを確認した結果

ご整理ありがとうございます。BridgeMod・DisplayMODのソースと設定、および要求が届く経路を確認するために必要なアプリ側送信処理を確認しました。資料だけで判断せず、現在の実装と、今後の変更案を分けて回答します。

1. **タイトル・サブタイトルは後勝ちです。** 表示中に別の要求が来ると、新しい表示へ切り替わります。音・粒子は前のものが残って重なる可能性があります。
2. **requestIdは実装済みです。** BridgeModはゲームMODへ同じ番号を渡します。eventKeyが同じという理由で削除・統合する処理はBridgeModにはありません。
3. **ゲームMOD内だけのリセットでは、古い要求が後から届く可能性があります。** BridgeMod側の待ち列と、アプリ側の未送信・再送待ちが別に残るためです。ただし、現在のアプリのMAP復元はBRIDGEとサーバーを停止する別の経路であり、この経路のメモリ上の待ち列は消えます。
4. **countと送信者名は1要求に保持されますが、個数には制限があります。** BridgeModの受付は1〜100で、アプリは100超を分割します。「任意のcountを1要求のまま無加工で渡す」という仕様とは完全には一致していません。
5. **ゲームMODから直接呼べるDisplayMOD公開APIがあります。** 呼ぶタイミングはゲームMOD側で決められます。ただし、表示時間・level・任意の追加引数は、現在すべて指定できるわけではありません。
6. **DisplayMODはOBSMODに依存していません。** OBSMODを呼ぶコードはなく、BridgeModにも必須依存していません。
7. **DisplayMODなしでもゲームを続行できる呼び出し方法を用意しています。** ゲームMOD側では、直接の必須依存ではなく、同梱のOptionalDisplayヘルパーを使う方法を推奨します。

StackingGame-Eventsのソースは今回の確認対象にありません。そのゲームMODが実際にどの受付API・リセット方法を使用しているかは確認できません。以下で「ゲームMOD側で対応」とした部分は、必要な受け口・連携条件を示しています。OBSMODの内部実装は、ご指定どおり確認・変更の対象外としています。

## 確認1：DisplayMODの表示が重なった場合

### 現在の答え

**A：後から来た表示へ切り替わる、です。** これはタイトル・サブタイトルについての答えです。

DisplayRenderer.showは、全接続プレイヤーに毎回次の順でパケットを送っています。

1. ClientboundSetTitlesAnimationPacket(10, 70, 10)
2. ClientboundSetSubtitleTextPacket
3. ClientboundSetTitleTextPacket

現在表示中か、ゲーム開始表示か、優先度はいくつか、といった状態を保持していません。そのため、AquaTowerの開始表示から0.5秒後に「ゾンビ襲来」を表示すると、タイトルとサブタイトルは「ゾンビ襲来」側へ置き換わります。

音と粒子は別です。前の音を停止する処理や、既に出した粒子を消す処理はないため、重なる可能性があります。画面全体の演出がすべて完全に置換されるという意味ではありません。

また、DisplayApi.showをサーバースレッド以外から呼ぶ場合はserver.executeでサーバースレッドへ処理を渡します。これはスレッドを合わせる処理であり、表示終了を待つための表示キューではありません。「後勝ち」は、サーバー側で実際に表示処理を実行した順で決まります。

### 最も実装しやすい方法

| 選択肢 | 実装の程度 | 注意点 |
|---|---|---|
| 1. 常に後勝ち | 現在のまま。最も簡単 | ゲーム開始表示も途中で切り替わる |
| 2. ゲーム開始表示だけ最低時間を守る | 表示種別と保護終了時刻など、小さな状態を追加すれば実装可能 | 保護中に届いた共通表示を省略するか、後で出すかの決定が必要。キューを作らないなら省略する仕様が明確 |
| 3. 簡単な優先度を付ける | 現在表示の優先度・有効期限・同順位の扱いを追加すれば実装可能 | 低優先度の扱いと期限が必要。優先度だけ追加して無期限に残さないようにする |

**現時点では1の「常に後勝ち」を推奨します。** コード変更が不要で、ゲームキューとも独立しています。開始表示が短すぎて読めないという問題が実際に確認された場合に、2を小さく追加する順がよいと考えます。大きな表示キューは追加しません。

2や3で表示を省略する場合は、タイトルだけでなく、その要求に付く音・粒子も同じ受付判定に含めるかを決める必要があります。

## 確認2：同じ要求の再送を見分けられるか

### 現在の要求番号

requestIdがあります。アプリのcreateModEventDeliveryが新規要求ごとにUUIDを作り、分割番号を付けます。同じHTTP送信を再試行する場合は、同じrequestIdを維持します。

BridgeEvent.fromJsonはその値を取り込み、executeEventSliceがGameEvents.offerへ渡します。互換用のeventIdにも同じ値を入れています。requestIdとeventIdの両方が送られた場合、異なる値は受け付けません。

requestIdは文字列です。現在は英数字・アンダースコア・ピリオド・コロン・ハイフンの1〜128文字を受け付けます。例の1001も文字列として渡します。

### ゲームMODへ渡る情報

主な項目は以下です。

| 意味 | 現在の実際の名前 |
|---|---|
| 要求番号 | requestId |
| イベント名 | key（ご説明のeventKeyに相当） |
| 個数 | count |
| 送信者名 | listenerName（ご説明のsenderNameに相当） |
| 入力種別 | type：gift／like／other |
| 表示要求 | announce |

serverと保護範囲の固定項目も渡します。任意のゲーム引数を自由に転送する仕組みは、まだありません。

### 重複排除をどこで行うか

**BridgeMod側でゲーム要求を一律に重複排除する必要はありません。** ご提示の方針どおり、ゲームMODが自分の待ち列へ登録する時点でrequestIdを確認します。

- 1001と1002は、同じイベント名・同じ送信者でも別要求として扱う。
- 同じ1001の再送だけを二重登録しない。
- キューが満杯でまだ受け入れていない要求には、WAITを返す。
- 本当に受け入れた時点で番号を記録する。
- 再送を受け取ったときは「既に引き受けた」と応答し、上流に無限再送させない。

現在のRequestLedgerはゲーム所有の台帳として使う補助クラスです。BridgeModがすべての要求を勝手に排除する仕組みではありません。採掘MODではこの方法で実機検証していますが、StackingGame-Events側の実装済みを意味しません。

共通の即時イベントは正常に届いた3件を3件処理します。現在は同じrequestIdの共通イベント再送も除外しない実装です。

外部からrequestIdを省略して送った場合、BridgeModが毎回新しい番号を作ります。その場合は再送と新規要求を識別できないため、ゲーム向けの再送では送信側も同じ番号を維持してください。

## 確認3：リセット後に古い要求が届く可能性

### 結論：ゲーム内だけのリセットでは可能性があります

実際のコードで次を確認しました。

- BridgeModはgift・like・otherに要求を保持する。
- tickごとの処理上限があるので、受信した要求がすべてその場で転送されるとは限らない。
- GameEvents.offerがWAITを返すと、要求をBridgeModの待ち列に残し、後で再度渡す。
- GameEventsの現行APIに、ゲーム終了・リセットをBridgeModへ通知して対象要求を失効させる処理はない。
- BridgeModの待ち列をまとめて消す処理は、サーバー停止時にある。
- アプリにも別の送信待ち列があり、HTTP失敗時は同じ要求番号で再試行する。通常運用では再試行回数は無制限。

したがって、以下の順は現在の実装で起こり得ます。

1. ゲーム固有要求RがBridgeModで待機する。例えば、ゲームMODがWAITを返している。
2. ゲームMOD側でリセットし、自分の待ち列を空にする。
3. BridgeModにはRが残っている。
4. ゲームMODが再び受け付けられる状態になる。
5. リセット前のRが転送され、新しいゲームへ登録される可能性がある。

これはコード上の到達可能な経路です。StackingGame-Events本体で実際に再現テストをしたという意味ではありません。

### アプリのMAP復元は別です

現在のアプリのrunMapOperationは、管理しているBRIDGEプロセスを停止し、Minecraftサーバーの保存・停止を待ってからMAPを復元します。アプリ側の送信待ち列はプロセス終了でなくなり、BridgeMod側の待ち列もonServerStoppingで消えます。

**このアプリの正規のMAP復元経路について、既存メモリ待ち列を消すための追加対応は不要です。** 外部の送信プログラムや、ゲームMOD内だけで行うMAP復元まで確認したという意味ではありません。

### 提案の比較

| 案 | 対応できる範囲 | 現在のコードに対する評価 |
|---|---|---|
| A. BridgeModの該当ゲーム要求を消す | 既にBridgeModが受け付けて保持している要求 | 変更は小さい。ただしアプリに残る未送信要求・HTTP再送は後から届くため、A単独では全経路を解決しない |
| B. ゲーム開始ごとの番号を付ける | 番号を付けた時点以降の送信待ち・転送待ちを含めて判定できる | 同一サーバーを維持してリセットする運用では、この1項目追加を推奨。ただし上流から番号を保持する必要がある |
| C. BRIDGEとサーバーを停止してからリセットする | 既存のメモリ待ち列を消せる | 現在のアプリのMAP復元はこの方法。ゲーム内リセットのたびに採用するには切断の影響が大きい |

同一サーバー上でゲームを繰り返す場合は、**Bのゲーム開始番号を最小限追加する案**を推奨します。表示キューや複雑な配信管理システムを増やす必要はありません。

仮の名前をgameSessionIdとすると、必要な契約は次です。

1. ゲームMODが現在のゲーム開始番号を管理し、Bridge側へ共有する。
2. ゲーム向けの新規要求を送信待ちへ登録するとき、その時点の番号を要求へ固定する。
3. 再送・転送では、その番号を書き換えずに運ぶ。
4. ゲーム終了・リセットでは古い番号を失効させる。次のゲームでは新しい番号を使う。
5. ゲームMODは現在と異なる番号の要求を登録しない。古い要求については再送を促すWAITではなく、消費・破棄を上流へ通知する契約にする。
6. 一時停止や、ゲーム継続中のプレイヤー死亡では番号を変えない。

**重要：BridgeModからゲームMODへ渡す瞬間に、常に最新の番号を付ける方法では対策になりません。** 古い要求が新しいゲームの要求に見えてしまうためです。アプリの送信待ち・再送も対象にするなら、新規要求の生成側から番号を保持する調整が必要です。

現行APIにはこの番号も、リセット通知の受け口もありません。名称と通知方法は提案段階です。BridgeModとDisplayMODのJARだけの変更に限定する場合、アプリ内の旧送信待ちまで含む完全な対策はできないことを明記します。

## 確認4：countと送信者名の受け渡し

### 1〜100の要求は、同じ要求に保持して転送できます

BridgeEventは、key・count・listenerName・requestIdを1つのオブジェクトで保持します。ゲームへの転送では、それぞれの要求から新しいMapを作ります。

- Aさん、count=3：Aさんの要求として保持。
- Bさん、count=2：Bさんの別要求として保持。
- 同じkeyという理由で2件をまとめる処理は、BridgeModにはありません。
- ゲーム経路では、BridgeModがcount回に展開してゲームイベントを実行することはせず、個数をゲームMODへ渡します。

GameEvents.offerは受け取ったMapをコピーして変更不能なMapとして受け口へ渡します。現在の固定項目を扱う範囲では、別ユーザーの名前と個数を混ぜる処理は確認できません。

### 現在の仕様との食い違い

**個数の上限：** BridgeEventのコンストラクターでcountを1〜100へ丸めます。アプリのcreateModEventDeliveryは100超を100ずつに分割します。例えばcount=150を、1件の「強さ150」としてそのままゲームへ渡すことは、現在の経路ではできません。

ご提示のcount=10の例は範囲内なので、ゲームMOD側で「10回」か「1回だけ強化」かを決められます。100超も元の1件のまま必要なら、BridgeMod側の受付制限だけでなくアプリの分割も調整する必要があります。共通Mob召喚の負荷制御まで一律に外す必要はありません。

**いいねのまとめ送信：** アプリ側のcreateLikeBatcherは、短時間に隣接した同一コマンド・同一送信者・同一表示条件を個数加算して送信します。異なる送信者はまとめませんが、同じ送信者による別々の発火が1件になる場合があります。

例えばゲームMODで「count=1を2回」と「count=2を1回」の意味が違うなら、合計が同じでも結果が変わります。ゲーム固有イベントをまとめない方針にする場合、この上流の処理から対象外にする必要があります。BridgeMod本体だけでは、既にまとめられた元の要求境界を復元できません。

**追加引数：** 現在のHTTP受付は固定項目しか読みません。argsなどをJSONに追加するだけではゲームMODへ転送されません。必要な項目名・型・上限・省略時の値を合意してから、要求ごとの情報として保持する変更が必要です。

## 確認5：ゲームMODからDisplayMODを実開始時に呼べるか

### 公開API

次の公開メソッドがあります。

`jp.douma.displaymod.api.DisplayApi.show(Object serverObject, Map<String, ?> payload)`

BridgeMod専用ではありません。ゲームMODは自分の待ち列からイベントを開始する箇所で呼べます。1回目開始時に1回、2回目開始時に1回、と呼び出し元で決められます。

ゲームMODからBridgeModへはGameEvents.registerで受け口を登録し、GAME_MOD／GAME_KEYメタ情報を使うAPI経路を接続します。この経路では、BridgeModはゲームMODへ渡した後、共通表示処理へ進まず戻ります。

旧方式のコマンド文字列でゲームMODを呼ぶ場合は、DISPLAY_OWNERをgameまたはnoneにしてBridge側表示を止める必要があります。新しいAPI経路と、古いコマンド経路は区別してください。

### 現在指定できるもの

| 項目 | 現在の対応 |
|---|---|
| title | 対応。空は不可。表示用に最大60文字へ整形 |
| subtitle | 対応。最大120文字へ整形 |
| 送信者名 | listenerNameで対応。senderNameという名前では解析しない。最大60文字へ整形 |
| count | 対応。DisplayMODでは1〜100,000の整数。表示文中の差し込み用であり、ゲーム実行回数を管理しない |
| sound | 登録済みサウンドのIDを文字列で指定。空文字で無効化。音量0.8・ピッチ1.0は固定 |
| particle | 登録済みのSimpleParticleTypeを指定。空文字で無効化。個数や広がりは固定 |
| duration／表示時間 | 未対応。10／70／10 tickで固定。20 TPSではフェードイン0.5秒・本表示3.5秒・フェードアウト0.5秒 |
| level | 未対応。強度を指すのか、対象ワールドを指すのかも確認が必要 |
| 表示対象プレイヤー・ワールド | 個別指定なし。全接続プレイヤーへ送る |
| 任意の追加項目 | 自動的に解釈しない。未対応キーを渡しても、その意味は反映されない |

表示文では`{ListenerName}`と`{Count}`を展開できます。`senderName`や`{senderName}`をそのまま使う契約ではありません。

### 小さく追加するなら

時間指定が必要なら、fadeInTicks・stayTicks・fadeOutTicksなど、単位を明記した任意項目を追加する方法が分かりやすいと考えます。省略時は現在の10／70／10を維持できます。durationという単一項目にする場合は、「本表示時間」か「フェードを含む合計時間」かを先に決めたいです。

levelは意味を確認する前に、強度やディメンションと決めつけて追加しません。ゲーム固有の強度を表示するだけなら、ゲームMODでsubtitleなどの文言を作って渡す方法もあります。

## 確認6：DisplayMODとOBSMODの分離

確認したDisplayMod・DisplayApi・DisplayRequest・DisplayRendererに、OBSMODを呼ぶ処理はありません。mods.tomlにも、OBSMODやBridgeModを必須とする依存宣言はありません。必須なのはMinecraftとForgeです。

DisplayMODは独立したJARです。`/displayevent`の診断用コマンドもあり、BridgeModなしで表示API・表示処理を利用できる構成です。

したがって、次の分離で問題ありません。

`ゲームMOD → DisplayMOD（Minecraft内の表示）`  
`ゲームMOD → OBSMOD（OBS側の演出）`

DisplayMODからOBSMODへ呼び出しを追加する必要はありません。OBSMODのSTART／END／CANCEL／RESET等の内部仕様は、こちら側の担当として本回答では扱いません。

## 確認7：DisplayMODがなくてもゲームを止めない

### 推奨する呼び出し方法

`examples/display-integration/OptionalDisplay.java`をゲームMOD側へコピーし、package名をゲームMOD固有の名前に変更して利用する方法を推奨します。

このヘルパーは次を行います。

1. DisplayMODのクラスとshowメソッドをReflectionで探す。
2. 見つからなければfalseを返す。
3. 呼び出しに失敗しても、ReflectiveOperationException・LinkageError・RuntimeExceptionを受け止めてfalseを返す。

ゲームMOD側では、DisplayMODを必須依存にせず、DisplayApiへの直接参照を避けます。MODの起動時点で必須依存エラーになる構成では、このヘルパーまで到達できないためです。

実開始処理での例です。OptionalDisplayは上記のヘルパーを自分のゲームMODへ取り込んだものとします。

```java
// ゲームMOD自身が「このイベントを今開始する」と決めた場所で呼ぶ。
OptionalDisplay.show(server, Map.of(
    "title", "AquaTower 開始",
    "subtitle", "{ListenerName} さん / 個数 {Count}",
    "listenerName", senderName,
    "count", count,
    "sound", "minecraft:entity.experience_orb.pickup",
    "particle", "minecraft:happy_villager"
));

// 戻り値がfalseでも、ゲームの開始は続行する。
// 続くOBSMOD呼び出しとゲーム本体の実行は、ゲームMOD側で制御する。
```

showがtrueを返しても、「受付・表示処理が行われた」ことを示す値であり、全プレイヤーが必ず見た保証や、表示完了通知ではありません。サーバースレッド外から呼んだ場合は後で表示処理が実行されます。開始順を合わせるなら、ゲームの開始処理も表示呼び出しもサーバースレッドで行う方法が明確です。

### アプリの標準装備との違い

MyGamePackアプリは、ユーザーの希望によりBridgeModとDisplayMODを標準装備として配置します。現在のアプリのゲーム切替は、同梱するDisplayMODのJARが欠けている場合に切替を中止します。

これはアプリの配布・切替方針です。ゲームMODの実行時依存とは別なので、そうてんもんさん側のゲームMODまでDisplayMODを必須依存にする必要はありません。DisplayMODなしの独立したForge構成でも、任意呼び出しでゲームを続行する設計にできます。
