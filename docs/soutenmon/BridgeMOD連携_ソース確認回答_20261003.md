# BridgeMOD・DisplayMOD・ゲームMOD・OBSMODの連携について

作成日：2026年10月3日  
確認対象：My-game-pack の PR #34 マージ後のソース  
確認コミット：`3b77bb2a66ba1e8324e89bab9fb4898378d2c54f`

## 1. 確認結果

ご提示いただいた「同じイベントが複数回来た場合」と「まったく同じ1件が通信再送された場合」を区別する方針は、今回の実装と一致しています。

BridgeMODは、イベント名が同じという理由で要求を削除・統合しません。要求ごとの識別番号をゲームMODまで渡し、ゲームMOD側で同じ要求の再送を判定する構成です。

ただし、今回ソースを確認できたゲームMODは採掘用のsaikutuMODです。AquaTower・UmetateMOD・RunMOD・OBSMODの実装ソースは、確認対象のリポジトリと作業フォルダーでは確認できませんでした。それらを含めて連携が完了しているとは回答できません。

## 2. 各MODの役割と確認できたこと

| MOD | ソースから確認できた動作 | 未確認・未実装の範囲 |
|---|---|---|
| BridgeMOD | gift・like・otherの3種類の待ち列、tickごとの処理上限、共通イベント処理、送信者名・要求番号の受け渡し、DisplayMODの呼び出し | 将来の全ゲームMODとの接続は未確認 |
| DisplayMOD | タイトル・サブタイトル・送信者名を含む文言・音・粒子の表示。BridgeMODやゲームMODから呼べる独立API | ゲームの待機・開始・終了・中止・順番待ちは管理しない |
| saikutuMOD | ゲーム固有イベントの受付、独自の待ち列、実行開始処理での表示呼び出し、同じ要求番号の再送判定 | 前の演出が完全に終わるまで次を待たせる、ゲーム全体の共通終了・中止・リセットAPIはない |
| AquaTowerなど、その他のゲームMOD | 実装ソースを確認できていない | 待機・順番・開始・終了・中止・リセット・countの意味・表示とOBSの呼び出しはコードから判断できない |
| OBSMOD | BridgeMOD・DisplayMOD・saikutuMODのソース内にOBSMODの呼び出しはない | OBSMOD本体のソースとAPI仕様を確認する必要がある |

BridgeMODの「共通表示」は、BridgeMODの内部で表示を描画するという意味ではなく、共通イベントの実行時に独立したDisplayMODを呼び出すという意味です。

## 3. 同じイベントと通信再送の区別

現在のsaikutuMODでは、次のように処理します。

| 受信内容 | 処理 |
|---|---|
| 同じイベント名・異なるrequestId | 別々の要求として、それぞれ登録・実行する |
| 同じrequestId・同じ内容の再送 | 二重登録しない |
| 同じrequestIdなのにイベント名・個数・送信者名などの内容が違う | 番号の不正な使い回しとしてエラーにする |

ご提示の例に対応させると、ゲームMOD側では次の考え方になります。

- requestIdが1001、AquaTower、Aさん：1件の要求。
- requestIdが1002、AquaTower、Bさん：1001とは別の要求なので、もう1件として扱う。
- requestIdが1001、AquaTower、Aさんの再送：最初の1001と同じ要求なので、二重登録しない。

これはAquaTower本体での動作確認結果ではなく、現在のsaikutuMODで実装・検証した方式をAquaTowerにも適用する場合の説明です。

### 要求番号を発行・維持する場所

アプリの送信処理で要求番号を発行し、同じ送信を通信エラーで再試行するときは、その番号を維持します。BridgeMODは受け取った番号をゲームMODまで渡します。

BridgeMODは、要求番号を省略した入力には新しい番号を発行します。そのため、外部から直接送る場合も、再送を判定してほしい要求には必ず同じrequestIdを付けてください。番号なしで再送すると、同じ1件かどうかを識別できません。

### 再送判定を記録するタイミング

ゲームMODが要求を待ち列へ受け入れた時点で、その番号を記録します。

待ち列が満杯で受け入れられない場合はWAITを返し、番号を受領済みとして記録しません。BridgeMOD側に要求が残るため、後で同じ要求を渡し直せます。

### 現在の再送判定の保存範囲

saikutuMODは、待ち列に残っている要求番号と、直近65,536件の処理済み要求番号をメモリ上に保持します。

- サーバー再起動をまたぐ永続保存はしていません。
- 処理済みの古い番号は、保持件数を超えると記録から外れます。
- 再起動後や記録から外れた後まで、永久に二重実行を防ぐ保証はありません。

再起動後の再送も防止する必要がある場合は、保存先・保存期間・ワールドのリセット時の扱いを決めて、別途対応する必要があります。

### 共通の即時イベント

共通のゾンビ召喚などは、届いた分をそのまま処理します。同じイベント名の別要求が3件届けば、3件処理します。

以前の方針に従い、共通イベントは同じrequestIdの再送も除外しません。同じ番号の共通イベントが2件届いた場合も、2件処理する実装です。ゲーム固有イベントの再送判定とは、この点を分けています。

## 4. 表示するタイミングと任意導入

### 共通イベント

1. BridgeMODが要求を受け付ける。
2. gift・like・otherの該当する待ち列へ入れる。
3. tickの処理上限に従って、共通イベントを実行する。
4. コマンドが実行されたことを確認した時点で、必要に応じてDisplayMODを呼ぶ。

### 現在のsaikutuMOD

1. BridgeMODが要求を受け付ける。
2. 要求番号・イベント名・個数・送信者名などをsaikutuMODへ渡す。
3. saikutuMODが再送を判定し、独自の待ち列へ登録する。
4. 実行できる状態になるまで待つ。
5. 待ち列からイベントの開始処理を行い、実行成功時にDisplayMODを呼ぶ。

BridgeMODは、ゲームMODへの受付時に先に表示を出しません。

厳密なコード上の順序は、採掘のエフェクト開始処理、または最初のコマンドの実行が成功してから表示APIを呼ぶ順です。将来のゲームMODで「表示とOBS通知を先に呼び、その直後に本体を開始する」順にしたい場合は、そのゲームMODの実開始処理内で制御します。

### DisplayMODが入っていない場合

BridgeMODとsaikutuMODは、DisplayMODのAPIを任意で呼び出す作りです。DisplayMOD未導入や呼び出し失敗の場合は、表示をスキップしてイベント本体を続行します。

DisplayMODは、タイトル・サブタイトル・音・粒子の表示を担当します。送信者名はlistenerNameとして受け取り、表示文の差し込みに使います。ゲームの順番待ちや進行は管理しません。

### OBSMOD

DisplayMODからOBSMODを呼ぶ処理はありません。

「ゲームMODが実際にイベントを開始する瞬間に、DisplayMODとOBSMODを別々に呼ぶ」という役割分担で接続する方針は可能ですが、現在のsaikutuMODにOBSMOD呼び出しは実装されていません。OBSMODのソースまたは公開API仕様を確認する必要があります。

## 5. 連携前に合わせたい具体的な仕様

### 5.1 引数名と型

現在、BridgeMODからゲームMODへ渡す主な項目は以下のとおりです。

| 項目 | 現在の引数名 | 内容 |
|---|---|---|
| 要求番号 | requestId | 文字列。新規要求は別番号、再送は同じ番号 |
| イベント名 | key | ご説明のeventKeyに相当 |
| 個数 | count | 1〜100の整数 |
| 送信者名 | listenerName | ご説明のsenderNameに相当 |
| 入力種別 | type | gift・like・other |
| 表示の要求 | announce | 表示を求めるかどうか。採掘MODでは実行開始処理で参照する |
| 旧名称の要求番号 | eventId | requestIdと同じ値を渡す互換用項目 |

内部呼び出しではserverと保護範囲関連の固定項目も渡します。

requestIdは現在、英数字・アンダースコア・ピリオド・コロン・ハイフンの1〜128文字を受け付けます。例の1001を渡す場合も、文字列として扱います。

### 5.2 countと分割の意味

現在のアプリは、100を超える個数を複数の送信要求へ分割します。各分割には別の番号を付け、同じ分割の通信再試行では番号を維持します。

AquaTowerなどでは、countが「実行回数」「高さ」「追加量」などのどれを意味するかを、イベントごとに合わせる必要があります。1つのゲームイベントを複数要求へ分割してよいかも、同時に確認したいです。

### 5.3 追加引数

現在のHTTP受付からゲームMODへの転送は、決められた項目を扱います。任意の追加引数をすべて自動転送する仕組みにはなっていません。

高さ・継続時間・対象などを必要とする場合は、項目名・型・上限・省略時の値を決めて、通信経路を拡張する必要があります。

### 5.4 受付・開始・終了を分ける

GameEventsのACCEPTEDは「ゲームMODが要求を引き受けた」という意味であり、イベントが開始・終了した意味ではありません。

現在のsaikutuMODでは、長い演出の処理を開始した段階で、その要求を待ち列から外してcompletedへ計上する場合があります。演出そのものの残りはeffectsPendingとして別に扱います。そのため、completedを「画面上の演出まで全部終わった件数」と解釈しないでください。

「前のイベントが完全に終了するまで次を開始しない」ゲームでは、その制御をゲームMOD側で実装する必要があります。終了・中止・リセットの通知方法と、途中で中止した要求を再実行するかも決めたいです。

### 5.5 待ち列の順番

gift・like・otherは独立した待ち列です。それぞれの待ち列内では先に受け付けたものから処理しますが、3種類すべてを横断した完全な到着順ではありません。ギフトの処理を優先し、いいねにも専用の処理枠を確保しています。

### 5.6 アプリ側のいいねのまとめ送信

BridgeMOD自体は要求を統合しません。一方、アプリ側には大量いいね対策として、短時間に隣接して届いた同じコマンド・同じ送信者・同じ表示条件の発火を、個数を維持してまとめて送る処理があります。既定のまとめる時間幅は1,200ミリ秒です。

これは実行個数を減らす処理ではありませんが、元の発火1件ごとに別々の要求番号を付ける方式ではありません。

「いいね由来の発火も必ず1件ずつ別番号で渡す」という条件がある場合は、このアプリ側の仕様も合わせる必要があります。

## 7. 検証済みの範囲

保存済みのForge 47.4.10での実機テスト結果と、対応するテストコードを確認しました。

- 同じ要求番号の再送を、ゲームMODの待ち列へ1件だけ登録する。
- 同じイベントでも別番号なら、別の要求として実行する。
- 処理済み要求の再送でも二重実行しない。ただし前述の記録保持範囲内に限る。
- ゲームMODが受け付けた時点では表示せず、実行開始処理で表示する。
- 共通イベントは、同じ番号の要求が2件届いても2件実行する。
- /bridgeから採掘MODのコマンドへ振り分ける。

AquaTower本体・OBSMOD本体との実際の接続テストを行った、という意味ではありません。

## 9. 現時点での回答

要求番号の受け渡しと表示機能の分離は対応済みです。ゲーム固有イベントの受付時にはBridgeMODで表示を先に出さず、ゲームMODの実際の開始処理で表示を呼べる構成になっています。

ゲーム固有の開始・終了・中止・リセット管理とOBS連携については、各ゲームMODとOBSMODのソースを確認しながら、引数と呼び出しタイミングを合わせたいです。
