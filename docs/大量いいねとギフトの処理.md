# 大量いいねとギフトの処理

2026年10月3日。BridgeアプリとBridgeMODの開発版での変更です。インストール済みアプリ・稼働用MODへの反映は保留しています。以下の動作には両方の更新が必要です。

## タラを出すペース

「100いいねでタラ1匹」なら、受信した新しいいいねが100増えるたびに1匹分を追加します。1,000いいねなら10匹分です。接続前の過去の累計や、同じ通知の重複は追加しません。

一度に何百匹も召喚せず、いいねによるタラは最短2tickに1匹、20TPS時に最大で毎秒10匹のペースで出します。同時に残すのは最大64匹です。上限に達したときは残りを待ち列に保持し、空きができてから出します。大量に届いた場合、出現し終わるまでの時間は長くなります。

いいねによるタラは、出現から400tick（20TPS時に約20秒）で消えます。自然に死んだ場合はそれより早く減ります。期限は魚の保存データにも記録し、チャンクの再読込で寿命が延びないようにします。以前のチャンクへ戻った際も、期限切れや上限を超える古い一時的な魚は再配置しません。ギフトで召喚した魚や、元からワールドにいる魚はこの整理の対象外です。

この制御は標準の `cod.txt` をいいねから呼んだ場合に適用します。任意の別名コマンドや、他の種類のMobすべてに個体数制限を設けたものではありません。

## 順番とギフトの優先

アプリのHTTP送信待ちとMOD内の実行待ちを、ギフト・いいね・その他の3種類に分けています。それぞれの種類の中では受け付けた順番を守ります。ギフトをいいねより優先するため、すべての種類を通した単一の時系列順ではありません。

いいねの送信先が満杯でも、ギフトの送信は別に進みます。MODはギフト側の処理予算を確保し、いいねは1tickあたり8コマンドの予算内で処理します。通常のtxtの1周分は途中で切り離さず、次の繰り返しを次tickへ回します。

HTTPの1リクエストは最大100回分とし、257回なら100・100・57に分けます。同じ種類では前のリクエストが受理されるまで次へ進みません。これは送信時のまとめ方であり、タラ257匹を1匹へ置き換えることではありません。いいねの短時間のまとめ送りも、隣接した同じコマンド・送信者・表示設定だけをまとめます。

空きがない場合はMODが429を返し、アプリが先頭のリクエストを保持して再送します。以前の「古いいいねを捨てる」「一定回数再送したら諦める」「5回・100回を超えた分を切り捨てる」処理は、BridgeMOD向けの経路から外しました。

2026-10-03の追加依頼で、再送の扱いを変更しました。各要求にrequestId（旧eventIdと同じ値）を付けて再送時も維持します。共通の即時イベントは届いた分を実行します。ゲーム固有イベントは番号をゲームMODへ渡し、ゲーム側で同じ1件だけ二重登録を防ぎます。saikutuMODは待機中の番号と完了最新65,536件を保持します。別の番号なら同じイベント名でもそれぞれ実行します。詳細は[採掘MODと統一コマンド](採掘MODと統一コマンド.md)を参照。

## 配信が終わったときのいいねの待ち

配信が終わったら（TikTok の配信終了 `streamEnd` を受けたら）、まだ実行していないいいね分を捨てます（2026-10-14 の決定）。大量のいいねが溜まっていても、配信のあとまで妨害が続かないようにするためです。

捨てるのは、アプリのいいねのまとめ送りの待ち、HTTP の送信待ち（再送の待ちを含む）、BridgeMOD のいいねの実行待ちの3か所です。BridgeMOD の待ちは、BridgeMOD 1.7.5 の `/bridge/control`（`{"action":"discard","type":"like"}`、トークンが必要）で捨てます。実行中のいいねは、その1周分を終えたところで止まります。配信終了のあとに届いたいいね（同じ通知のまとまりに残っていた分など）は、次に TikTok へつながるまで使いません。送信中だった分が捨てたあとに BridgeMOD へ着くことがあるので、2秒後にもう一度捨てさせます（そのあいだに次の配信へつながっていたら、新しい配信のいいねを捨てないよう、捨て直しません）。送信中にすでに届いていた分は、送れたものとして履歴に残します。

配信中のいいね、ギフト、そのほかのイベント、テスト発火は捨てません。`/bridge/control` もいいね以外の種類は受け付けません。捨てた回数と件数はログに出します。

## いいね・フォローのマイルストーン

いいねマイルストーン（`options.gameplay.likeMilestones`）は、1回のいいねの通知で配信の累計いいねが threshold を越えたときに1回発動します（2026-10-14 の決定）。配信の途中からつないだときは、つなぐ前に越えていたマイルストーンは発動しません。以前は、最初の通知でまとめて発動していました。BRIDGE を止めずに次の配信へつないだときは、累計が0から数え直されるので、また発動します。

フォローマイルストーン（`followMilestones`）は、つないでからのフォローの数で数えます。別の配信（TikTok の配信の番号 roomId が変わったとき）につないだら0から数え直し、同じ配信へのつなぎ直しでは続きから数えます。テスト発火も、いいねマイルストーンを本番と同じ判定（前回の累計から今回の累計までに越えたもの）で確かめます。

## 確認した範囲と限界

- 本番のTikTok受信ハンドラーへ15,700いいね相当を入力し、157匹分の送信を確認しました。
- 送信先が8回続けて混雑を返しても、回数・送信者・順序を保持し、その間にギフトを送れることを確認しました。
- Minecraft 1.20.1 / Forge 47.4.10、サーバーヒープ2GB、CPU利用数2の隔離ワールドで、いいね120件・ギフト20件を検証しました。
- タラ120匹と名前付きゾンビ20体が欠落・重複なく実行され、それぞれの待ち列の順番も一致しました。
- 水槽内でタラが残り続ける条件でも同時数64匹以内となり、いいね由来の魚だけが期限で消えました。
- この試験で観測したサーバー平均tick時間の最大値は6.52ms、TPSの最小値は20でした。ギフトを送ってから実行を確認するまでの最大時間は140msでした。MinecraftクライアントのFPSを測定した値ではありません。

待ち列は稼働中のメモリにあります。アプリやサーバーの終了・クラッシュをまたぐ永続保存、TikTokから届かなかった通知の復元までは対応していません。また、コマンド自体の誤り・対象プレイヤー不在・重い別MODなどまで成功を保証するものではありません。ギフトの発動開始順は守りますが、長く続く演出をすべて終了させてから次のギフトを開始する方式ではありません。

RCON / 7 Days to Dieの従来経路は今回の変更対象外です。負荷試験の再実行方法は `BridgeMod/test/README.md`、テスト本体は `BridgeMod/test/like-load.cjs` を参照してください。
