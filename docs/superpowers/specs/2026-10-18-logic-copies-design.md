# 処理のコピーの食い違いをなくす（設計書）

- 日付: 2026-10-18
- 出どころ: アプリレビュー 2026-10-08「同じロジックのコピーが少しずつ食い違っている（config_schema が2つ、コマンドのメタ情報の読み方が4種類、ゲーム ID の正規表現が6か所以上）」（HANDOFF04 の9番、残っている大きい問題「処理のコピー」）
- 今の状態の調べ: 2026-10-18、main `c113907`（読むだけの調べ。結果は下の 4〜10 に書いた）

## 1. 目的

- 同じ仕事をするコードが何か所にもあり、少しずつ食い違っている。同じ入力でも、アプリ・BRIDGE・MOD のどこを通るかで結果が変わる。
- 食い違いを全部なくし、どこから使っても同じ決まりで動くようにする。
- 配信中に効く食い違い（ギフトが黙って消える、配信画面の表示が化ける、配信中に保存した設定が効かない）を先に直す。

## 2. ユーザーの決定（2026-10-18）

- 食い違いは全部直す。配信中に効かないもの（保存・ゲームの切り替え・配信前チェックのときだけのもの）も直す。
- BridgeMOD（Java）も直す。問題の元が MOD にあるもの（`.` のある名前を探せない、BOM を読み飛ばさない）は MOD で直し、MOD の版を上げる。配信者はアプリを更新してサーバーを起動し直せば、今の txt のまま動く（jar はアプリが入れ替える）。
- 配信中に保存した設定は、BRIDGE を再起動しなくても効くようにする（下の 8）。
- 今より厳しくする確かめ（回数・いいねの閾値）は、保存済みの設定をアプリの更新のときに1回だけ直してから、どこでもエラーにする（下の 7）。

## 3. 決まりの置き場（作りの方針）

- JavaScript の共通の決まりは、今の `bridge/command_files.cjs` と同じく `bridge/` の `.cjs` に置き、electron は `../bridge/…` から読む。新しい `shared/` フォルダーは作らない（今の形に合わせる。bridge は配布物に入るので、electron から読める）。
- 画面（`src/`）は、決まりの処理を自分で持たない。データ（ゲーム ID の一覧など）が要るときは、`bridge/` の JSON を読み込むか、main から ipc で受け取る。どちらにするかは作る人が決める。
- Java（BridgeMOD・SaikutuMod・DisplayMod）は JavaScript とコードを分け合えない。同じ決まりを Java にも書き、**同じ例の一覧（JSON）を JavaScript のテストと Java の契約テストの両方で読み**、同じ結果になることを確かめる。例の一覧は決まりごとに1つ置く。
- 同じ動きの小さい関数（`clampInt`（`bridge/index.js`）と `boundedInt`（`bridge/event_rules.cjs`））は1つにする。

## 4. コマンド名（`.` のある名前）

- 今: アプリ・BRIDGE（`bridge/command_files.cjs` の `BRIDGE_COMMAND_KEY`）・MOD の受け付け（`BridgeMod.java` の fromJson）は `[A-Za-z0-9_.-]{1,200}` を受け付ける。MOD がファイルを探す所（`CommandRouting.java` の `resolve`）だけが `[A-Za-z0-9_-]+` で、`.` を許さない。
  - `tnt.v2.txt` のような名前は、アプリの TXT 作成でも作れ、どの確かめも通り、MOD は HTTP 202 で受け取る。そのあと MOD は「file not found」として捨てる。BRIDGE は 202 で成功とみなすので、統計とテスト発火には成功と残る。
- 直し方: `CommandRouting.resolve` も `[A-Za-z0-9_.-]{1,200}`（`.txt` を除いた部分）を受け付ける。`/`・`\` は今までどおり含まないので、フォルダーの外は指せない。
- `.txt` の付け外し（今は約8通り）は、`bridge/command_files.cjs` の1組の関数にまとめ、大文字の `.TXT` も `.txt` と同じに扱う（Windows のファイル名は大文字小文字を区別しない。MOD も区別しない）。`electron/game_command_scope.cjs`・`electron/gift_templates.cjs` の `endsWith('.txt')` などもこれを使う。

## 5. コマンド txt の見出し行（`# TITLE:` など）

- 今の読み方は7つある: BRIDGE（`bridge/index.js` の `parseCommandFile`）、BridgeMOD（`BridgeMod.java` の `parseFile`）、アプリの一覧（`electron/bridge_settings.cjs` の `readCommandMetadata`）、ルーレット（`bridge/roulette.cjs`）、SaikutuMod（`SaikutuMod.java`。同梱ファイルだけ）、開発用（`vite.config.ts`）、テスト（`standard-commands`・`tiktok-events`）。
- 決まり（今の BRIDGE の読み方に合わせる）:
  - 見出し行は、前後の空白を除いて `#` で始まり、`# キー: 値` の形の行。キーは英字と `_` だけ（`TITLE2` のような数字入りは見出しとして扱わない）。大文字小文字を問わず、大文字にそろえる。`#` とキー、キーと `:` の間の空白はあってよい。
  - ファイルの先頭の BOM は無視する。CRLF も LF も同じに読む。
  - 同じキーが2つあれば、後の行を使う。
  - 値が空（`# TITLE:` だけ）の行は、そのキーが「ない」ものとする。次の行を値として拾わない。
  - 説明文は、最初の `//` で始まる行で、`//` のあとが空でないもの。次の行にまたがらない。
- JavaScript は1つのモジュールにまとめ（例: `bridge/command_meta.cjs`）、上の7つのうち JavaScript のもの（BRIDGE・アプリの一覧・ルーレット・開発用・テスト）はすべてそれを使う。
- Java（BridgeMOD の `parseFile`、SaikutuMod）も同じ決まりにする。BOM を読み飛ばし（BOM 付きの1行目がコマンドとして実行され、`# COUNT_MODE:`・`# DESTRUCTIVE:` を読み落とすのを止める）、キーの形・大文字へのそろえ方・空の値の扱いを合わせる。
- 見出しの例の一覧（JSON）を1つ置き、JavaScript と Java の両方のテストで読む。

## 6. ゲーム ID とゲーム専用のコマンド

- ゲーム ID の一覧（common・umetate・run・saikutu）は1か所（`bridge/` の JSON など）に置き、`electron/game_profiles.cjs`・`electron/game_command_scope.cjs`・`electron/games_ipc.cjs`・画面（`CommandsListPage.tsx`・`src/lib/devApiMock.ts`）はそこから読む。Java（`CommandRouting.java`）の一覧は契約テストで同じことを確かめる。5つ目のゲームを足すときに直す所を減らす。
- 「ゲーム専用のコマンドか」の判定は1つの関数にする。決まり: `game_<一覧にあるゲーム>_` で始まる名前だけがそのゲーム専用。それ以外（`game_mode_on.txt` など）は共通のコマンド。今の汎用の判定（`game_profiles.cjs` の `/^game_[a-z0-9]+_/`、main の設定の復元の `startsWith('game_')`）もこの関数にそろえる。
- ゲーム MOD の ID（`^[a-z][a-z0-9_]{1,63}$`、予約名 bridgemod・displaymod・doumacmd）とゲームパックのコマンド key（`^[a-z][a-z0-9_]{0,49}$`）も、JavaScript は1つの関数にし、Java（`GameEvents.java`）とは契約テストで合わせる。

## 7. 設定（config.minecraft.json）の確かめと既定値

- 確かめ（スキーマ）は1つにする。`bridge/config_schema.js` を正本にし、electron（保存・`config:validate`・プリセットの読込・配信前チェック・バックアップの一覧）も同じものを使う。今の2つの違いは次のように決める:
  - TikTok ID が空のときの文は、アプリの文（「IDを承認する」を案内する方）にそろえる。
  - BridgeMOD が受け付けない名前: 保存済みの設定にある名前は、どこでも「警告」（BRIDGE も起動し、その割り当ては送らない）。アプリの保存で新しく足した名前は「エラー」で保存を止める。「新しいか」は、保存済みの設定に同じ**コマンドの名前**があるかで決める（今は「ギフト割り当て（バラ）」のような表示名込みの場所で比べていて、ギフト名やいいねの閾値を変えるだけで保存が止まる）。配信前チェックとバックアップの一覧も同じ決まりで数える（バックアップの一覧は、送り方を消して数えるのをやめる）。
- 今どちらも確かめていないものを足す:
  - `repeat` は 1〜100 の整数（文字列の `"3"` や `2.5` もエラー）。ギフト割り当て・各イベント・ルーレットとデスルーレットの項目・コメントギフトのルール・コンボなど、設定の中の `repeat` すべてが対象。`enabled: false` の項目も確かめる（あとで有効にされるため）。今の BRIDGE は文字列を数に直し、100 を超えると黙って 100 にしていた。今の画面（`EventSettingsPage.tsx`・`EventSettings2Page.tsx`）は 2.5 も保存できる。
  - いいねの閾値は 1 以上の整数。今の画面は負の数や小数も保存できる。
  - TikTok ID（下の 9）。
  - 画面の入力欄も、整数だけを受け付けるようにする（新しく正しくない値を入れられないように）。
- `commandTransport` は、空（RCON）か、知っている送り方の名前（`command_files.cjs` の一覧）だけを正しいとする。知らない名前（`"bridge-mod"` のような書き間違い）は、どこでも「警告」にして RCON として扱う（今と同じ動きに、警告を足す）。直し方を推測できないので、下の更新のときの直しでも書き換えない。
- **保存済みの設定は、アプリの更新のときに1回だけ直す**（ユーザーの決定 2026-10-18）。
  - 直す前に、今の設定のバックアップ（`settings_backups.cjs`）を取る。
  - 直し方: `repeat` は四捨五入して 1〜100 に収める（`"3"` → 3、`2.5` → 3、`500` → 100、数にならないもの → 1）。いいねの閾値は四捨五入して 1 以上にする（0・負の数・数にならないもの → 1）。上の対象すべて（`enabled: false` も）に行う。
  - 直したことは、ログに残し、配信者にも一度だけ知らせる（何を直したかと、バックアップがあること。出し方は作る人が決める）。
  - 直したあとは、上の確かめは**どこでもエラー**にする（アプリの保存・配信前チェック・BRIDGE の起動。BRIDGE は起動しない）。手で書き換えて正しくない値を入れた場合も同じ。
  - 古い設定を読み込む所（設定のバックアップの復元・プリセットの読込・ギフトのテンプレートの適用）でも、同じ直しを通してから確かめる（古いバックアップを戻せなくならないように）。
  - 「1回だけ」をどう覚えておくか（設定の中の版の番号など）は作る人が決める。
- 既定値（`options` の各値、新しい設定の雛形）は1つのモジュールに置き、BRIDGE・`electron/paths.cjs`・`scripts/prepare-bridge-runtime.cjs` はそれを使う。
  - 送り方: 設定に無いときは RCON（今の BRIDGE・アプリの判定と同じ。BridgeMOD より前の設定のため）。新しい設定の雛形には `bridge_mod` を書く（今と同じ）。
  - コマンドの場所（`commandsDir`）: 設定に無いときは `commands/minecraft`（今の BRIDGE は `commands` で、アプリ・ルーレットと食い違う）。コマンドの場所を決める処理（BRIDGE・ルーレット・アプリの4通り）は1つの関数にする。
- 画面の古い名前をなくす: 運用センター（`OperationsPage.tsx`）の `likeBatchMs`・`likeCatchupLimit` は `likeBatchWindowMs`・`maxLikeCatchUpPerEvent` だけにする。配信ホーム（`DashboardPage.tsx`）が書く `commandsDir: "commands/minecraft"`（保存のたびに main が上書きするので効いていない）は消す。`src/lib/devApiMock.ts` も合わせる。
- BridgeMOD のホスト・ポートの読み方（前後の空白を除く、旧い `doumaMod*` の名前、ポートの既定 25576）は1つの関数にし、BRIDGE と `electron/bridge_mod_client.cjs` が使う。
- `bridge/index.js` の既定値のコメントが `electron/main.cjs` を指している所を直す。

## 8. 配信中に保存した設定を、再起動なしで効かせる

- 今: 設定の再読込（`bridge/index.js` の `reloadDynamicConfig`）は設定全体を確かめるのに、反映するのはギフトの割り当てと各イベントだけ。`options` は起動のときに1回読むだけで、画面にも「再起動で反映」の案内がない。
- 保存したらすぐ効かせるもの:
  - 運用センターの6つ: ミュートする視聴者（`mutedUsers`）、読み上げの NG ワード（`ttsNgWords`）、ギフトのクールダウン（`giftCooldownMs`）、1ギフトのコマンドの上限（`maxCommandsPerGift`）、いいねの追いつきの上限（`maxLikeCatchUpPerEvent`）、いいねをまとめる時間（`likeBatchWindowMs`）。
  - そのほかの `options`: 知らないギフトのログ（`logUnknownGifts`）、アナウンス（`announce*`）、ゲームの設定（`gameplay`。時限倍率など。今の状態（いいねの累計・連打など）は保ったまま、設定だけ差し替える）、ブロックを守る範囲（`protection`）。
  - （作る人の判断）上の一覧は「つなぎ方」以外の `options` 全部、という考え方。ほかに見つけた `options` も同じ考え方で決めてよい。
- 再起動が要るもの（つなぎ方）: TikTok ID、送り方（`commandTransport`）、BridgeMOD のホスト・ポート、RCON（`rcon`・`target`）、コマンドの場所（`commandsDir`）。BRIDGE が動いている間にこれらを変えて保存したら、画面に「BRIDGE を再起動すると反映されます」と出す。BRIDGE は今の値のまま動き続け、ログにも同じことを出す。
- 再読込で設定にエラーがあるときは、今と同じく直前の設定のまま動き続ける。

## 9. TikTok ID

- 今の判定は3つ: スキーマ（空でないことだけ）、配信前チェック（`/^[\w.]{1,24}$/`）、LIVE の確かめ（小文字にしてから `/^[a-z0-9_.]{1,24}$/`）。`foo-bar` は BRIDGE は接続しにいき、ほかの2つはエラーにする。
- 1つの関数にする: 前後の空白と先頭の `@` を除き、小文字にして、`[a-z0-9_.]{1,24}` に合うか。スキーマ・配信前チェック・LIVE の確かめ・BRIDGE の接続がすべて使う。合わない ID はスキーマのエラーにする（BRIDGE も起動しない。どうせ接続できないため）。

## 10. そのほかの食い違い

- **設定の中のコマンドの参照の数え方**（今は4つ: `command_files.cjs`・`preflight.cjs`・`game_command_scope.cjs`・`game_profiles.cjs`）を1つにする。
  - コメントのコマンド・投票の文字列の値（`{"!猫":"missing.txt"}`）も数える（今の配信前チェックは見ていない）。
  - `enabled: false` の設定（イベント・ギフト割り当て）は、参照として数えず、BRIDGE も動かさない。今の BRIDGE はギフト割り当ての `enabled` を見ずに動かすが、画面にギフト割り当ての有効・無効はないので、手で書いた設定だけが変わる。
  - （私の判断）無効のギフト割り当てに当たるギフトが届いたら、何もしない。「未設定ギフト」（`unmappedGiftEvent`）にも回さない（無効にしたつもりのギフトで妨害が出ないように）。ゲームの設定の数え方（ギフトの上位者・連打・時限倍率の回数など）は、割り当ての有無に関係なく今と同じにする。
- **ギフト割り当ての整え方**（今は5つ: BRIDGE の起動・再読込、`gift_mapping.cjs`、`gift_templates.cjs`、`DashboardPage.tsx`）を1つにする（giftId の前後の空白を除く、名前が空なら `gift:<giftId>`、`.txt` を付ける、`repeat` は上の 7 の決まり）。
- **音・粒子の ID の確かめ**: JavaScript（`event_rules.cjs`・`roulette.cjs`）を DisplayMod（`DisplayRequest.java` の `(?:[a-z0-9_.-]+:)?[a-z0-9_./-]+`、200文字まで）に合わせる。受け取る側（DisplayMod）が正しい（`a:b:c` は Minecraft の ID として正しくない）。例の一覧で両方を確かめる。

## 11. 変えないこと・やらないこと

- 画面の見た目・ipc の名前は変えない（8 の「再起動で反映」の案内を出す所と、7 の古い名前を消す所だけ画面に手を入れる）。
- アプリの設定（app-config.json）の既定値と、設定ファイルが壊れたときにログイン状態などが消える問題は、別の大きい問題「設定の既定値と設定ファイルの破損」で扱う。ここでは config.minecraft.json の既定値だけをまとめる。
- `bridge/index.js` の分割はしない（必要な所だけ共通のモジュールへ出す）。
- MOD のコマンドのファイルの探し方（環境変数と2階層上まで探す処理）は、サーバー側の事情なので Java のまま残す。既定の場所（`commands/minecraft`）が JavaScript と同じであることだけ合わせる。

## 12. 進め方（PR を分ける）

配信中に効くものから先に出す。1本ごとに `npm run verify` と CI（MOD のビルドを含む）が通り、ユーザーの許可を得てマージしてから次へ進む。PR ごとに実装計画を作る。

1. **コマンド名と見出し行**（4・5）: BridgeMOD の `.` のある名前と BOM、見出しの決まりを JavaScript・Java でそろえる、`.txt` の扱い。BridgeMOD と SaikutuMod の版を上げる。
2. **配信中に保存した設定の反映**（8）: 再起動なしで効かせる、再起動が要るものの案内。
3. **設定の確かめと既定値**（7・9）: スキーマを1つに、BridgeMOD が受け付けない名前の決まり、足す確かめ、既定値・コマンドの場所・ホストとポート・TikTok ID、画面の古い名前。
4. **参照の数え方・ギフト割り当て・ゲーム**（6・10）: 参照の数え方、`enabled`、ギフト割り当ての整え方、ゲーム ID の一覧とゲーム専用の判定、MOD ID、音・粒子の ID、小さい関数の重複。

- 3 と 4 は、作る人がもっと細かく分けてもよい。
