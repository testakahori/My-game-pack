# 設定ファイルが壊れても消えないようにする（設計書）

- 日付: 2026-10-23
- 出どころ: HANDOFF04 の「次の大きい問題」の「設定の既定値と設定ファイルの破損」（10-14 のアプリレビューの表の「設定の既定値が3か所にあり、設定ファイルが壊れるとログイン状態なども消える」）。処理のコピーの設計書（2026-10-18）の 11 で、別の大きい問題として外したもの。
- 今の状態の調べ: 2026-10-23、main `320f57f`（読むだけの調べ。結果は下の 3）。
- 実際に壊れたことはまだない（ユーザー 10-23）。起きる前に防ぐ直し。

## 1. 目的

- 配信者それぞれの PC で動くアプリなので、設定ファイルが壊れても、ログイン・サーバーのフォルダー・ギフト設定・読み上げなどを失わないようにする。
- 壊れる元は2通りある（ユーザー 10-23）。配信者の PC で壊れた（PC が落ちた・電源が切れたなど）ときは、配信者から不具合の連絡が来る。開発中のアップデートで壊したときは、直した版のリリースノートに「壊してしまったので戻しました」と書く。どちらの場合も、あとで何が起きたか分かる記録を残す。

## 2. ユーザーの決定（2026-10-23）

- 壊れていたら、配信者に聞かずに、前の正しい状態へ自動で戻す。
- 壊れていたことは、アプリの画面には出さない。壊れたファイルは名前を変えて残し、ログに「壊れていたので戻した」と書くだけにする（不具合の連絡が来たときに調べられるように）。
- 直す範囲は、アプリの設定だけでなく、下の 4 のファイル全部。
- アプリの設定の既定値を1か所にまとめる。

## 5. 共通の決まり（守るファイルすべて）

### 5.1 書くとき

- 壊れにくい書き方にする。別のファイル（一時ファイル）に書き、ディスクに確実に残す指示（fsync）をしてから、元のファイルと差し替える。今の `atomicWrite`（`electron/settings_backups.cjs`）に fsync を足して使うか、新しい共通の関数にするかは作る人が決める。守るファイルを書く所は、すべてこれを通す（`paths.cjs:77`・`bridge_sync.cjs:607` の無防備な所も）。
- 書く前に、今のファイルが正しく読めるなら、その中身を「前の正しい状態の写し」として残す（ファイルごとに1つ。名前は作る人が決める。例: `app-config.json.last-good`）。今のファイルが壊れているときは、写しを上書きしない（壊れた中身で正しい写しを消さない）。

### 5.2 読むとき

- 「壊れている」とは、次のどれか。
  - 読めない、または JSON として読めない（空のファイル・途中で切れたファイル・0 が並んだファイルを含む）。
  - 中身がオブジェクトでない（`null`・配列・数・文字列）。
  - ファイルごとに決めた、なくてはならない項目の型が違う（下の 6。例: アプリの設定の `serverFolder` が文字列でない）。
- 設定として未完成・確かめのエラーがある（例: ギフト設定のスキーマのエラー、TikTok ID が未承認）のは「壊れている」ではない。今までどおり扱う（保存の確かめ・配信前チェック・BRIDGE の警告やエラー）。
- 壊れていたら:
  1. 壊れたファイルを消さずに、名前を変えて残す（例: `app-config.json.broken-20261023-153012`。名前の付け方は作る人が決める。何度も壊れたときに前の記録を上書きしない）。
  2. 前の正しい状態の写しがあれば、それを元のファイルとして書き戻し、その中身で動く。配信者には何も聞かない。
  3. 写しも無い（または写しも壊れている）ときは、今までと同じ既定値で動く。壊れたファイルは 1 のとおり残っているので、上書きで失われることはない。ただしギフト設定は既定値の雛形を作らない（下の 6.4）。ゲームの切り替えの記録の扱いは下の 6.5。
  4. ログに1行書く（下の 5.3）。
- 画面には出さない（ユーザーの決定）。

### 5.3 ログ

- アプリ（main）は `userData/logs/settings-recovery.log` に書き足す（停止の記録 `logs/stop-requests.log`（`electron/stop_requests.cjs`）と同じ形）。1行に、時刻・どのファイルか・どう壊れていたか（読めない／オブジェクトでない／項目の型）・何をしたか（写しから戻した／写しが無いので既定値）・残した壊れたファイルの名前。
- BRIDGE（読み上げの設定の BRIDGE 側の写しを読むとき）は、今の BRIDGE のログ（`bridge/logs/bridge-*.log`）に同じ内容を書く。
- ログのファイルが書けなくても、アプリと BRIDGE は止めない。

### 5.4 決まりの置き場

- 処理のコピーの設計書（2026-10-18）の 3 のとおり、アプリと BRIDGE の両方が使う決まり（読み上げの設定の読み方）は `bridge/` の `.cjs` に置き、electron は `../bridge/…` から読む。アプリだけが使うもの（アプリの設定・ギフト一覧の画面の設定・ゲームの切り替えの記録）は `electron/` に置いてよい。どこに置くかは作る人が決める。
- 1つの共通の関数（読む・書く・壊れていたら戻す・記録する）にまとめ、守るファイルはどれもそれを使う。ファイルごとに違うのは「なくてはならない項目の型」と「既定値」だけにする。

## 6. ファイルごとの決まり

### 6.1 アプリの設定 `app-config.json`

- 既定値と項目の型は1か所の表にまとめ、main と型の宣言がそれを使う（表の形・置き場所は作る人が決める。ギフト設定の `bridge/config_defaults.json` と同じ形にしてよい）。今の既定値（フォルダーは空・セットアップは未完了。項目ごとの暗黙の既定は今のまま）を変えない。
- 「壊れている」の項目の型: 少なくとも `serverFolder`（文字列）・`setupComplete`（真偽）・ログインの3項目（文字列）。ほかの項目も、表に型を書いたものは確かめる。型の違う項目が1つでもあれば、ファイル全体を壊れていると扱う（項目ごとに直すのはしない）。
- 開発用のブラウザー表示（`src/lib/devApiMock.ts`）の値は、見本としてわざと違う値（セットアップ済み・ログイン済みなど）にしているので、そのままにする。
- 型の宣言（`src/types/electron.d.ts`）を、main が受け付ける項目と返す項目に合わせる。
- ログインの状態は、アプリの設定と一緒に前の正しい状態の写しにも入る（どちらも同じ PC の userData の中なので、守り方は同じ）。設定のバックアップ（`settings_backups.cjs`）には、今までどおりログインを入れない。

### 6.2 読み上げの設定（2か所）

- 2か所とも 5 の決まりで書き、読む。
- BRIDGE 側の写しが壊れていたら、BRIDGE は前の正しい状態の写しから戻す。写しも無ければ、userData 側の正しい中身があればそれを使う。どちらも無いときだけ既定値。読み上げを切っていた配信者が、壊れたせいで読み上げが動き出すことを避ける。

### 6.3 ギフト一覧の画面の設定 `gv-settings.json`

- 5 の決まりで書き、読む。壊れていて写しも無ければ、TikTok ID が空の既定値（今の「ファイルが無い」と同じ）。

### 6.4 ギフト設定 `config.minecraft.json`

- 今の安全な書き方に、前の正しい状態の写しを足す。読む所で壊れていたら写しから戻す（BRIDGE を起動する前に、アプリが戻しておく）。
- 写しから戻す前に、ゲームの切り替えの記録と合っているかを確かめる（下の 6.6）。
- 写しも無い（または 6.6 で合わない）ときは、既定値の雛形を作らない（私の案）。壊れたファイルの写しを 5.2 の 1 のとおり別の名前で残したうえで、元の場所には壊れたファイルをそのまま置く。雛形（TikTok ID も割り当ても空）で動くと、配信者からは理由も分からずにギフト設定が消えたように見えるため。
  - 配信前チェックは今までどおり「設定を読み込めません。初期セットアップと設定バックアップを確認してください」と案内する（`electron/preflight.cjs:20-24`）。
  - その案内どおりに戻せるよう、ギフト設定が読めないままでも次の操作は止めない。
    - 設定のバックアップから戻す（今は今の設定を読めずに止まる。戻す前の確かめで今の設定を使っている所（ゲームの選択・RCON・接続の項目）は、今の設定が読めなければバックアップと既定の側の値を使う。使い方の細かい所は作る人が決める）。
    - アプリの設定の保存（ゲームの切り替えの記録を読む所が、ギフト設定を確かめずに読んで止まっている）。
    - ゲームの一覧（`games:list`）。
  - ファイルが無いときに雛形を作る所（`paths.cjs` の `ensureConfigExists` など）は、壊れたファイルが置いてある間は作らない（ファイルがあるので、今の作りのままで作らない）。

### 6.5 ゲームの切り替えの記録 `profiles.json`・`pending-switch.json`

- 5 の決まりで読む（書き方は今のまま安全）。壊れていたら写しから戻す。戻す前に、ギフト設定と合っているかを確かめる（下の 6.6）。
- 写しも無い（または 6.6 で合わない）ときの扱い（切り替えの途中の記録をどう扱うか）は作る人が決める。ただし、アプリの設定の保存・ギフト設定の保存・ゲームの一覧・設定のバックアップから戻す操作が止まらないようにする。

### 6.6 ギフト設定とゲームの切り替えの記録を写しから戻すとき（私の案）

- ゲームの切り替え（`game_profiles.cjs` の `activate`）は、ギフト設定と切り替えの記録の2つを続けて書く。写しはファイルごとに書く前の中身なので、片方だけを写しから戻すと、ギフト設定の「今のゲーム」（`gameProfile`）と、記録の「今のゲーム」（`active`）が食い違うことがある。
- 食い違ったまま配信者がゲームを選び直して保存すると、片方のゲームの保存済みの設定が、もう片方のゲームの割り当てで上書きされて消える（例: 採掘から RUN に切り替えた直後にギフト設定が壊れ、写しから採掘のギフト設定に戻ったあと、採掘を選んで保存すると、RUN の設定が採掘の割り当てで上書きされる）。
- そこで、どちらかを写しから戻す前に、戻した中身の「今のゲーム」が、もう片方（壊れていない方）の「今のゲーム」と合うかを確かめる。合わなければ自動では戻さず、写しも無いときと同じ扱い（6.4・6.5）にする。確かめ方の細かい所は作る人が決める。

## 9. テスト

- 守るファイルごとに、壊れた中身（空・途中で切れた JSON・`null`・配列・文字列・なくてはならない項目の型の違い）で読むと、前の正しい状態の写しから戻り、壊れたファイルが名前を変えて残り、ログに1行書かれること。

- 書く所がすべて共通の関数を通ること（`fs.writeFileSync` で守るファイルを直接書く写しが残っていないことを、本文を探すテストで見張る。処理のコピーの設計書 13 と同じ考え）。

- ログイン状態の確かめが失敗したら、ログイン画面が出ること。

## 11. 作るときに私（Claude）が決めたこと

ユーザーと決めたことではなく、設計を書くときに私が決めたこと。違っていれば直す。

- 「前の正しい状態の写し」はファイルごとに1つだけにする（何世代も残さない）。戻ると、最後の1回の保存が失われることがある。
- 書いた中身をディスクに確実に残す指示（fsync）を足す（電源が切れたときにも途中の状態が残りにくくするため）。
- 型の違う項目が1つでもあれば、ファイル全体を壊れていると扱う（項目ごとに直さない）。
- ログイン状態の確かめが失敗したときは、ログイン画面を出す側に直す。
- 開発用のブラウザー表示の見本の値は変えない。
- ログは画面のログ欄ではなく `userData/logs/settings-recovery.log`（と BRIDGE のログ）に書く（アプリの画面のログ欄はメモリの中だけで、アプリを閉じると消えるため）。
- ギフト設定が壊れていて写しも使えないときは、空の雛形で動かさず、壊れたファイルを置いたまま、今の配信前チェックの案内（設定のバックアップから戻す）と、読めないままでも使える「バックアップから戻す」で直してもらう（6.4。設計書を読んだ読み手の問いから）。
- ギフト設定とゲームの切り替えの記録は、写しから戻す前に「今のゲーム」が合うかを確かめ、合わなければ自動では戻さない（6.6。読み手の問いから）。
