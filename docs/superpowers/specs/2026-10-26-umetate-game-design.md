# 埋め立てをアプリのゲームにする 設計書（2026-10-26）

## 1. 何をするか・なぜ

埋め立ては、配信者（プレイヤー1人）が研究室マップの3階の中央にある枠をブロックで埋めきれば勝ち、視聴者は TikTok のギフトで妨害する（ときどきお助けもする）ゲーム。
MOD（UmetateMod。中身はそうてんもんさんの StackingGame-Events と、ユーザーが Codex と足した研究室の仕組み）と専用マップはもうある（PR #145 で main に入る）。
今は、アプリのゲームの一覧に「埋め立て」の名前があるだけで、選んでも遊べない。これを、採掘と同じように TOP で選べば遊べるゲームにする。

「形になったら」次に、採掘のイベント用の専用マップ（ユーザーが作って配る）に進む。そのため、マップの仕組みは、あとで採掘の複数のマップを載せられる形にしておく。

## 2. ゲームの決まり（ユーザーの決定）

- プレイヤーは1人。
- 勝ち：3階の中央の枠の内側を、金ブロックとダイヤブロックで、1マスの空きもなく埋める（金も数に入る）。
  - 全部埋まったら、10 からのカウントダウンが始まる。
  - カウントダウンの途中で、枠の中のブロックが1つでも金・ダイヤでなくなったら、カウントダウンは止まる。
  - 0 になったら、花火が上がり、キラキラのエフェクトが出て、黄緑色の文字で「congratulation」がタイトルに出る。そして、枠の中のブロックが全部消える。
- 視聴者のギフトで起きること：そうてんもんさんの13個のイベント、`umetate` の妨害・お助け（下の 3.1）、BridgeMOD の標準のコマンド（爆発・ゾンビなど）。どのギフトに何を割り当てるかは、配信者がアプリで決める（今と同じ）。

## 3. やること

### 3.1 UmetateMod：コマンドを `umetate` にそろえる

- そうてんもんさんのイベントを、`umetate <イベントの名前>` で動かせるようにする（ユーザーの決定）。例：`umetate nether_army` は今の `stackgame run nether_army` と同じ。
  - 対象は、MOD で実際に動く13個：aquatower・magmatower・aquarium・voidbomb・voidbomb_rain・megablast・nether_army・void_singularity・meteor_shower・meteor_purge・tornado・orbital_laser・shockwave_collapse（`UmetateMod/src/main/resources/event-master/events.master.json` で `implementationStatus: "implemented"` のもの）。
  - 一覧にあるだけで中身の無い10個（gift_spawn_zombie・creeper・skeleton、gift_buff_* 3個、gift_debuff_* 4個。`candidate`）は作らない（2026-10-26 ユーザーの決定）。ゾンビ・効果などは BridgeMOD の標準のコマンドを使う。
  - 形は `umetate <名前> [回数] [送った人]`（PR1 で決めた。3.2 の「回数」）。イベント固有の値と `--sender 名前` を受けるのは、今までどおり `stackgame run` の形。
  - `stackgame run` などの今の形は残す（私の判断。そうてんもんさんの元の使い方と、今の検証を壊さないため）。
  - `umetate` の下の名前は、今ある6つ（otasuke・mofumofu・stamp・atamahuttou・zigoku・reset）とぶつからない。ぶつかる名前が将来できたら、今ある6つが勝つ（私の判断）。
- 勝ちの判定（2 の決まり）を MOD に入れる。
  - 枠の内側の範囲は X・Z が −6〜6、Y が 49〜64（13×13×16＝2704マス。2026-10-26 ユーザーの決定「16段」）。`otasuke` は今のまま Y 49〜56（下半分）を金で埋める。
  - MOD のアリーナの範囲（`StackingConfig` の `max-y`。今の既定は 56）も 64 に広げる。アリーナで起きるイベントや保護が、枠の上半分にも届くようにするため。サーバーにすでにある MOD の設定ファイルに 56 が書かれていても、64 になるようにする（作り方は作る人が決める）。作る前に、研究室マップの実物で、枠の内側が Y 49〜64 で、その上が空いていることを確かめる。
  - 判定は研究室マップのワールド（`umetate_lab_map.json` で見分けているもの）でだけ動かす。
  - カウントダウンの見せ方（タイトルの数字・音など）、花火の数、キラキラのパーティクルの種類は、作る人が決めてよい。文字は「congratulation」（ユーザーの言葉どおり）、色は黄緑（Minecraft の `green`）。
  - 止まったあと、また全部埋まったら 10 から数え直す（私の判断）。
  - `reset`・`zigoku` など、研究室の処理が動いている間の扱いは、作る人が既存の処理（同時に動かさない決まり）に合わせて決める。
- ギフトの表示（だれのギフトで何が起きたか）は、イベントが始まったときに UmetateMod が DisplayMOD に出させる（2026-10-26 ユーザーの決定。採掘と同じ形）。
  - 今の UmetateMod は、DisplayMOD を `giftsdisplay` という MOD ID で探していて（標準装備の DisplayMOD の ID は `displaymod`）、しかも本番のイベントでは呼ばず、試しの `stackgame test display` でだけ呼ぶ（`IntegrationService.java`）。名前を直すだけでは出ない。
  - 採掘の `SaikutuMod` の `OptionalDisplay.java`（DisplayMOD が無くても動く呼び方）と同じ形で呼ぶ。ゲームパックのコマンドは今の既定（`DISPLAY_OWNER: game`。`commonDisplay` は付けない）のまま。
  - `umetate` の5つ（otasuke など。ギフトに載せるもの）も、ギフトから動いたときは同じく表示する。
- 版を上げ、jar の印（`<jar>.inputs.json`）と、Forge なしの確かめ（`scripts/test-soutenmon-contracts.cjs`）を今の作り方どおりに通す。

### 3.2 アプリ：埋め立てのゲームパック

- `game-packs/umetate/game.json` を作る（採掘の `game-packs/saikutu/game.json` と同じ形）。
  - 載せるコマンド：13個と、otasuke・mofumofu・stamp・atamahuttou・zigoku の5つ（合わせて18）。名前（key）は MOD の名前をそのまま使い、タイトルは日本語（13個は `events.master.json` の `displayName`、5つは HANDOFF・`map/README.md` の説明から付ける）。
  - `reset` は載せない（推測：配信者が使うもので、ギフトには割り当てない）。配信者は、ゲームの中で `/umetate reset` を打って使う。アプリにボタンは作らない（私の判断）。
  - `destructive`（保護エリアの中では動かさない印）は、どのコマンドにも付けない（2026-10-29 ユーザーの決定「妨害マイクラなんだからマップボッコボコにしていい」）。
  - 回数：コマンドは `umetate <名前> [回数] [送った人]` の形（2026-10-26 ユーザーの決定「umetate mofumofu 1 のように」。採掘の `saikutu` と同じ形）。ゲームパックのコマンドは `umetate <名前> {Count} {ListenerName}` と書き、`bridgeEventApi` は使わない（BridgeMOD がこのコマンドを、回数を入れて1回だけ打つ）。回数は MOD が受け取って、その数だけ起こす（PR1 で作った）。強さに上限は付けない（2026-10-10 のユーザーの決定）。
    - BridgeMOD は、`{Count}` のあるコマンドでも1回に100回分までしか入れない（`BridgeMod.java` の `MAX_COUNT`）。250 なら 100・100・50 の3回打たれ、そうてんもんさんのイベントなら待ち行列に3つ入り、表示も3回出る（数は合う）。
    - そうてんもんさんの13個：待ち行列には1つで入り、回数の分だけ続けて起きる。`/umetate reset`・取り消しでは残りも捨てる。死んだときは残りを続ける。3階の復元中・地震のあいだに届いても、待ち行列に入れて、終わってから起こす（2026-10-26 ユーザーの決定）。
    - 研究室の5つ：名前ごとの順番待ちに並べ、回数の分だけ1秒おきに起こす。黒曜石スタンプ・頭沸騰は、毎回その時のプレイヤーの位置をねらう（追いかける）。地獄は何回でも落ちる（いまの地獄が終わってから次）。処理中は待つ。`/umetate reset` は順番待ちも捨てる（2026-10-26 ユーザーの決定。最後のレビュー 重要4）。
- 配る：UmetateMod の jar を、サーバーと Minecraft 本体の両方に入れる（白い光や揺れの描画のため、本体にも要る。`map/README.md`）。
  - `scripts/mod_jars.cjs` で、UmetateMod を「作るだけ」（`buildOnlyModJars`）から、ゲームパックの jar に移す。
  - `scripts/prepare-game-packs.cjs` は今は採掘だけを決め打ちで作る。埋め立ても作れるようにする。
- ギフトの割り当ての一覧に出るのは、埋め立てを選んだときだけ（今の `game_umetate_*.txt` の決まりのまま。チャットでは `/bridge nether_army` などになる）。

### 3.3 アプリ：マップの入れ替え

- 埋め立ての初期のマップ（研究室マップ）を、アプリと一緒に配る。
  - 元は `map/umetate_lab_map`（約53MB。git の外）。配る前に、プレイヤーのデータ（`playerdata`・`stats`・`advancements`）を外す（私の判断。作った人のアカウントの記録を配らないため）。`umetate_lab_map.json`（研究室の見分け）は残す。
  - git には入れない（今のまま。ユーザーの「フォルダーは軽く」）。配る物を作るとき（`npm run release:win` の準備の手順）に `map/umetate_lab_map` から写し、無ければはっきり止まる。テストは小さな見本のワールドで行う。
- サーバーのフォルダーに `map_backup` を作り、初期のマップをそこに入れておく（ユーザーの決定）。アプリを入れた・更新したあと、最初に使うときに配った物から写す。
- ほかのゲームから埋め立てに切り替えるたびに（ユーザーの決定）。埋め立てを選んだまま TOP の「保存」を押したときは、マップに触らない（2026-10-26 ユーザーの決定「ゲームが変わったときだけ」）：
  1. `map_backup` の初期のマップを、使うマップのフォルダーへ写す（写し終えたことを確かめてから次へ）。
  2. 前に使っていた（壊れた）埋め立てのマップを消す。
  3. サーバーが写したマップを読むようにする（`server.properties` の `level-name`）。
  - 使うマップの場所は `haihu_world/umetate_lab_map`（私の判断。サバイバルの `haihu_world/world` と並べる）。
  - 今の切り替え（`electron/game_profiles.cjs` の `activate`）と同じく、サーバーが止まっているときだけ行い、途中で失敗したら元に戻す（MOD・コマンドの入れ替えと同じ記録で戻す）。
- 採掘・サバイバルに切り替えたときは、マップに触らない（ユーザーの決定）。`level-name` は、埋め立てに切り替える前に使っていたワールドに戻す（私の判断。今は採掘もサバイバルも `haihu_world/world`）。
- 今ある手での導入に出会っても壊さない：ユーザーの配信サーバー（`server/Douma_Craft`）は、10-25〜26 に Codex がアプリを通さずに、`level-name=umetate_lab_map`（サーバーのフォルダーの直下）と UmetateMod 2.6.22 にしてある。
  - 埋め立てに切り替えるときは、アプリが置く `haihu_world/umetate_lab_map` を使い、直下の `umetate_lab_map` は消さない（アプリが置いた物ではないため。私の判断）。
  - 採掘・サバイバルに切り替えるとき、「埋め立ての前に使っていたワールド」の記録が無ければ `haihu_world/world` に戻す（私の判断）。
- 「マップを初期化」ボタン（ユーザーの決定）：押すと、今のゲームの初期のマップを `map_backup` から写し、古いマップを消して、写したマップを使うようにする。
  - 今は埋め立てだけ。サバイバルには出さない（推測）。採掘は、専用マップができたときに足す。
  - サーバーが動いている間は押せない（理由を出す）。押したら確かめの画面を出す（古いマップは消えて戻せないため）。
  - 置き場所は TOP のゲームを選ぶ所の近く（私の判断）。
  - 遊んでいる途中の3階の作り直しは、サーバーを止めずに済む `umetate reset` もある（Codex の作業）。初期化のボタンは、それでは戻らないときや、まるごと最初に戻したいとき用。

## 4. やらないこと

- 採掘の専用マップ（何個か用意して選ぶ）。埋め立てのあとに別の作業でする。ただし `map_backup` と「マップを初期化」は、ゲームごとに複数のマップを持てる形にしておく。
- サバイバルのマップの初期化。
- 勝ち負けの記録・回数の集計、アプリの画面での勝ちの知らせ（勝ちは MOD がゲームの中で知らせる）。
- 強さの上限・間引き（2026-10-10 のユーザーの決定）。

## 5. 守ること

- 本物の配信サーバー（`server/Douma_Craft`。ジャンクション）と、ふだんの設定（`%APPDATA%\tiktok-bridge-ui`）は、テストや確かめで書き換えない。一時のサーバー・一時の設定で確かめる（HANDOFF04 の PR3 の「本物のアプリでの確かめ」のやり方）。
- `.bat`・`.cmd` は英語だけで書く。
- 画面の文は日本語。
- いつもの流れ：計画 → テストを先に書く → 最後に opus のレビュー → ブランチ・PR・CI → ユーザーの許しでマージ → HANDOFF04 の docs PR。

## 6. 作る人に任せること

- `umetate <イベント>` の作り（今の `StackGameCommand` の受け方を共通にするなど）。
- カウントダウン・花火・キラキラの細かな見せ方（2 の決まりの中で）。
- ゲームパックの各コマンドのタイトル・カテゴリーの言葉、`destructive` を付ける一覧（PR に書く）。
- マップの写し方・確かめ方（今の `electron/map_saves.cjs` の確かめながら写す処理を使えるなら使う）。
- PR の分け方（例：1. UmetateMod のコマンドと勝ちの判定、2. ゲームパックと配り方、3. マップの入れ替えと初期化のボタン）。
